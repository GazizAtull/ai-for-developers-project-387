# Критерии ревью календаря звонков

Используются авторевью (`.github/workflows/review.yml`) и человеком перед мержем.

## Что считается дефектом

1. **Занятый слот не должен оставаться доступным.** После брони её интервал `[start, end)` исчезает из `/availability` для всех типов встреч, повторная или пересекающаяся запись (в том числе частичное наложение встреч разной длительности) получает `409 SLOT_TAKEN`. Примыкание (11:00 после 10:00–11:00) разрешено.
2. **Правила бронирования только на сервере.** Проверка пересечений и запись под одним замком в `CalendarService`. Проверка только во фронтенде дефект: прямой запрос в API её обходит.
3. **Контракт первичен.** Поля, пути, коды и тела ответов совпадают с `contract/main.tsp`. Ручные правки `openapi.yaml` и `frontend/src/api/` запрещены; меняется TypeSpec и запускается `mise run generate`.
4. **Фронтенд ходит в API только через сгенерированный SDK** (`src/api.ts`), без ручного `fetch`.
5. **Окно и расписание не меняются без спецификации:** 14 дней с сегодняшнего, пн–пт 09:00–18:00 Asia/Almaty, шаг 30 минут, слот = длительность типа.
6. **Ошибки данных** дают `400 VALIDATION_ERROR` с понятным `message`, гость видит сообщение, а не падение страницы.
7. **Соседний сценарий не регрессирует.** Изменение не ломает обычную запись (без новых полей) и список владельца.
8. **Тесты на новое поведение есть** на нужном уровне: домен (`CalendarServiceTest`), HTTP-контракт (`ApiContractTest`), браузер (`frontend/e2e/`), включая негативный сценарий.
9. **Объём согласован.** PR ссылается на исходное обращение, спецификацию, тикеты и комментарий согласования; изменение не выходит за согласованный объём.
10. **Секретов в коде и логах нет.**

## Формат замечания

`файл:строка` — условие, при котором ошибка проявляется — последствие (кого и что затронет). Без пересказа вывода линтера. Если подтверждённых дефектов нет, так и сказать.

## Глубина проверки по риску

| Изменение | Что проверять перед мержем |
|---|---|
| Тексты и подписи интерфейса | Соответствие задаче и отображение |
| Новое необязательное поле брони | Контракт и генерация, валидация, основной и негативный сценарии, бронь без поля |
| Расчёт слотов и пересечений | Основной сценарий, пересечения разных типов, примыкание, параллельные запросы |
| Права и воркфлоу GitHub Actions | Доступ к коду и секретам, отдельное решение человека |
